你写了一个 skill，用一个 prompt 试了一下，看起来能工作。但它是否可靠？面对多样化 prompt 和边界情况时表现如何？是否比完全没有 skill 更好？运行 structuredeval（evals）可以回答这些问题，并为系统改进 skill 提供反馈循环。

## 设计测试用例

一个测试用例包含三部分：

- **prompt**：真实感较强的 user 消息，也就是 user 实际可能输入的内容。
- **预期输出**：用人类可读的方式 description 成功是什么样子。
- **输入 file**（可选）：skill 需要处理的 file。

将测试用例存放在 skill directory 内的 `evals/evals.json` 中：

```json evals/evals.json
{
 "skill_name": "csv-analyzer",
 "evals": [
 {
 "id": 1,
 "prompt": "I have a CSV of monthly sales data in data/sales_2025.csv. Can you find the top 3 months by revenue and make a bar chart?",
 "expected_output": "A bar chart image showing the top 3 months by revenue, with labeled axes and values.",
 "files": ["evals/files/sales_2025.csv"]
 },
 {
 "id": 2,
 "prompt": "there's a csv in my downloads called customers.csv, some rows have missing emails — can you clean it up and tell me how many were missing?",
 "expected_output": "A cleaned CSV with missing emails handled, plus a count of how many were missing.",
 "files": ["evals/files/customers.csv"]
 }
 ]
}
```

**编写优秀测试 prompt 的建议：**

- **从 2 到 3 个测试用例开始。** 在看到第一轮结果前不要过度投入。之后可以扩展集合。
- **改变 prompt。** 使用不同措辞、细节程度和正式程度。有些 prompt 应较随意（“hey can you clean up this csv”），另一些应更精确（“Parse the CSV at data/input.csv, drop rows where column B is null, and write the result to data/output.csv”）。
- **覆盖边界情况。** 至少包含一个测试边界条件的 prompt，例如格式错误的输入、不寻常请求，或 skill instructions 可能含糊的情况。
- **使用真实 context。** 真实 user 会提到 file 路径、列名和个人 context。像“process this data”这样的 prompt 太模糊，测试不到有用内容。

暂时不用担心定义具体通过/失败检查，只需要 prompt 和预期输出。看到第一轮运行结果后，再添加详细检查（称为 assertion）。

## 运行 eval

核心模式是每个测试用例运行两次：一次**带 skill**，一次**不带 skill**（或使用旧版本）。这样你就有了可比较的基线。

### 工作区结构

将 eval 结果组织在与 skill directory 并列的工作区 directory 中。完整 eval 循环的每一轮都有自己的 `iteration-N/` directory。在其中，每个测试用例都有一个 eval directory，并包含 `with_skill/` 和 `without_skill/` 子 directory：

```
csv-analyzer/
├──SKILL.md
└──evals/
 └──evals.json
csv-analyzer-workspace/
└──iteration-1/
 ├──eval-top-months-chart/
 │ ├──with_skill/
 │ │ ├──outputs/ # Files produced by the run
 │ │ ├──timing.json # Tokens and duration
 │ │ └──grading.json # Assertion results
 │ └──without_skill/
 │ ├──outputs/
 │ ├──timing.json
 │ └──grading.json
 ├──eval-clean-missing-emails/
 │ ├──with_skill/
 │ │ ├──outputs/
 │ │ ├──timing.json
 │ │ └──grading.json
 │ └──without_skill/
 │ ├──outputs/
 │ ├──timing.json
 │ └──grading.json
 └──benchmark.json # 聚合统计
```

你手动编写的主要 file 是 `evals/evals.json`。其他 JSON file（`grading.json`、`timing.json`、`benchmark.json`）会在 eval 过程中由 agent、 script 或你生成。

### 启动运行

每次 eval 运行都应从干净 context 开始：不包含之前运行或 skill 开发过程遗留的状态。这能确保 agent 只遵循 `SKILL.md` 中的 instructions。在支持 subagent 的环境中（例如 Claude Code），这种隔离很自然：每个子 task 都是全新开始。如果没有 subagent，请为每次运行使用单独 session。

每次运行请提供：

- skill 路径（基线运行则不提供 skill）
- 测试 prompt
- 所有输入 file
- 输出 directory

下面是一次带 skill 运行时你可以给 agent 的示例 instructions：

```
Execute this task:
- Skill path: /path/to/csv-analyzer
- Task: I have a CSV of monthly sales data in data/sales_2025.csv.
 Can you find the top 3 months by revenue and make a bar chart?
- Input files: evals/files/sales_2025.csv
- Save outputs to: csv-analyzer-workspace/iteration-1/eval-top-months-chart/with_skill/outputs/
```

对于基线，使用同一个 prompt，但不提供 skill 路径，并保存到 `without_skill/outputs/`。

改进现有 skill 时，请使用前一个版本作为基线。编辑前先为它创建快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），让基线运行指向该快照，并保存到 `old_skill/outputs/` 而不是 `without_skill/`。

### 捕获计时数据

计时数据让你比较 skill 相对基线消耗了多少时间和 token。一个显著提升 output quality 但让 token 用量变为三倍的 skill，与一个质量更好且成本更低的 skill，是不同的权衡。每次运行完成后，记录 token 数和耗时：

```json timing.json
{
 "total_tokens": 84852,
 "duration_ms": 23332
}
```

<Tip>
在 Claude Code 中，subagenttask 完成时，[task 完成通知](https://platform.claude.com/docs/en/agent-sdk/typescript#sdk-task-notification-message)包含 `total_tokens` 和 `duration_ms`。请立即保存这些值，因为它们不会持久化到其他地方。
</Tip>

## 编写 assertion

assertion 是关于输出应包含什么或达成什么的可 validation 陈述。请在看到第一轮输出后再添加它们，因为在 skill 运行之前，你往往并不知道“好”是什么样子。

好的 assertion：

- `"The output file is valid JSON"`：可通过程序 validation。
- `"The bar chart has labeled axes"`：具体且可观察。
- `"The report includes at least 3 recommendations"`：可计数。

弱 assertion：

- `"The output is good"`：太模糊，无法评分。
- `"The output uses exactly the phrase 'Total Revenue: $X'"`：太脆弱；措辞不同但正确的输出会失败。

并不是所有内容都需要 assertion。有些质量（写作风格、视觉设计、输出是否“感觉正确”）很难拆解为通过/失败检查。这些更适合在[人工审查](#reviewing-results-with-a-human)中 discovery。请把 assertion 留给能客观检查的内容。

将 assertion 添加到 `evals/evals.json` 中的每个测试用例：

```json evals/evals.json highlight={9-14}
{
 "skill_name": "csv-analyzer",
 "evals": [
 {
 "id": 1,
 "prompt": "I have a CSV of monthly sales data in data/sales_2025.csv. Can you find the top 3 months by revenue and make a bar chart?",
 "expected_output": "A bar chart image showing the top 3 months by revenue, with labeled axes and values.",
 "files": ["evals/files/sales_2025.csv"],
 "assertions": [
 "The output includes a bar chart image file",
 "The chart shows exactly 3 months",
 "Both axes are labeled",
 "The chart title or caption mentions revenue"
 ]
 }
 ]
}
```

## eval 输出

评分是指根据实际输出 eval 每个 assertion，并用具体证据记录 **PASS** 或 **FAIL**。证据应 reference 或指向输出，而不只是表达观点。

最简单的方法是把输出和 assertion 交给 LLM，并要求它逐项 eval。对于可用代码检查的 assertion（有效JSON、正确行数、 文件存在且尺寸符合预期），请使用 validation script。对于机械检查，script 比 LLM 判断更可靠，也能跨迭代复用。

```json grading.json
{
 "assertion_results": [
 {
 "text": "The output includes a bar chart image file",
 "passed": true,
 "evidence": "Found chart.png (45KB) in outputs directory"
 },
 {
 "text": "The chart shows exactly 3 months",
 "passed": true,
 "evidence": "Chart displays bars for March, July, and November"
 },
 {
 "text": "Both axes are labeled",
 "passed": false,
 "evidence": "Y-axis is labeled 'Revenue ($)' but X-axis has no label"
 },
 {
 "text": "The chart title or caption mentions revenue",
 "passed": true,
 "evidence": "Chart title reads 'Top 3 Months by Revenue'"
 }
 ],
 "summary": {
 "passed": 3,
 "failed": 1,
 "total": 4,
 "pass_rate": 0.75
 }
}
```

### 评分原则

- **PASS 必须有具体证据。** 不要给模糊空间。如果 assertion 说“包含摘要”，而输出只有一个标题为“Summary”的章节和一句模糊句子，那就是 FAIL：标签在，但实质不在。
- **审查 assertion 本身，而不只是结果。** 评分时留意哪些 assertion 太容易（无论 skill 质量如何都会通过）、太难（即使输出很好也总是失败）或不可 validation（无法仅凭输出检查）。在下一轮迭代中修复它们。

<Tip>
比较两个 skill 版本时，可以尝试**盲评**：把两个输出都交给 LLM 评审，但不透露哪个来自哪个版本。评审会按自己的标准为整体质量打分，例如组织结构、格式、可用性和完成度，不会受“哪个版本应该更好”的偏见影响。这是 assertion 评分的补充：两个输出可能都通过所有 assertion，但整体质量差异很大。
</Tip>

## 聚合结果

当本轮迭代的每次运行都评分后，按配置计算汇总统计，并将其保存到 eval directory 旁的 `benchmark.json`（例如 `csv-analyzer-workspace/iteration-1/benchmark.json`）：

```json benchmark.json
{
 "run_summary": {
 "with_skill": {
 "pass_rate": { "mean": 0.83, "stddev": 0.06 },
 "time_seconds": { "mean": 45.0, "stddev": 12.0 },
 "tokens": { "mean": 3800, "stddev": 400 }
 },
 "without_skill": {
 "pass_rate": { "mean": 0.33, "stddev": 0.10 },
 "time_seconds": { "mean": 32.0, "stddev": 8.0 },
 "tokens": { "mean": 2100, "stddev": 300 }
 },
 "delta": {
 "pass_rate": 0.50,
 "time_seconds": 13.0,
 "tokens": 1700
 }
 }
}
```

`delta` 告诉你 skill 的成本（更多时间、更多 token）以及收益（更高通过率）。一个增加 13 秒但把通过率提高 50 个百分点的 skill 可能值得。一个让 token 用量翻倍却只提升 2 个百分点的 skill 可能不值得。

<Note>
标准差（`stddev`）只有在每个 eval 有多次运行时才有意义。在只有 2 到 3 个测试用例且每个只运行一次的早期迭代中，请关注原始通过数量和 delta。随着你扩展测试集并多次运行每个 eval，统计指标才会变得更有用。
</Note>

## 分析模式

聚合统计可能掩盖重要模式。计算 benchmark 后：

- **移除或替换在两种配置中总是通过的 assertion。** 这些 assertion 无法提供有用信息，model 在没有 skill 的情况下也能处理好。它们会抬高带 skill 的通过率，却不反映真实 skill 价值。
- **调查在两种配置中总是失败的 assertion。** 要么 assertion 有问题（要求 model 做不到的事），要么测试用例太难，要么 assertion 检查了错误内容。请在下一轮迭代前修复。
- **研究带 skill 时通过、不带 skill 时失败的 assertion。** 这是 skill 明确创造价值的地方。理解*为什么*：哪些 instructions 或 script 产生了差异？
- **当多次运行结果不一致时收紧 instructions。** 如果同一个 eval 有时通过、有时失败（在 benchmark 中体现为高 `stddev`），eval 可能不稳定（对 model 随机性敏感），或 skill instructions 足够含糊，导致 model 每次解释不同。添加示例或更具体指导以减少歧义。
- **检查时间和 token 异常值。** 如果某个 eval 耗时是其他 eval 的 3 倍，请阅读其 execution 转录（model 在运行期间做了什么的完整日志）以找到瓶颈。

## 人工审查结果

assertion 评分和模式分析能捕捉很多问题，但它们只检查你想到并写成assertion 的内容。人工审查者能带来新视角：discovery 你没有预料的问题，注意到输出虽然技术上正确但没有抓住重点，或 discovery 难以表达成通过/失败检查的问题。对每个测试用例，请同时审查实际输出和评分。

记录每个测试用例的具体反馈，并将其保存在工作区中（例如作为 eval directory 旁的 `feedback.json`）：

```json feedback.json
{
 "eval-top-months-chart": "The chart is missing axis labels and the months are in alphabetical order instead of chronological.",
 "eval-clean-missing-emails": ""
}
```

“图表缺少坐标轴标签”是可操作的；“看起来不好”则不是。空反馈表示输出看起来没问题，该测试用例通过了你的审查。在[迭代步骤](#iterating-on-the-skill)中，请把改进重点放在你有具体抱怨的测试用例上。

## 迭代 skill

评分和审查后，你有三类信号来源：

- **失败 assertion**指向具体缺口：缺失步骤、不清晰 instructions，或 skill 未处理的情况。
- **人工反馈**指向更广泛的质量问题：方法错误、输出结构差，或 skill 产出了技术上正确但没有帮助的结果。
- **execution 转录**揭示问题*为什么*发生。如果 agent 忽略了一条 instructions，instructions 可能含糊。如果 agent 把时间花在低效步骤上，这些 instructions 可能需要简化或移除。

把这些信号转化为 skill 改进的最有效方法，是将三者连同当前 `SKILL.md` 一起交给 LLM，并要求它提出修改建议。 LLM 可以综合失败 assertion、审查者抱怨和转录行为中的模式，而这些模式手动关联起来会很繁琐。提示 LLM 时，请包含以下准则：

- **从反馈中泛化。** skill 会用于许多不同 prompt，而不只是测试用例。修复应广泛处理底层问题，而不是为具体示例添加狭窄补丁。
- **保持 skill 精简。** 更少、更好的 instructions 往往胜过详尽规则。如果转录显示存在浪费工作（不必要 validation、不需要的中间输出），请移除这些 instructions。如果添加更多规则后通过率停滞，skill 可能被过度约束；尝试移除 instructions，看看结果是否保持或改善。
- **解释原因。** 基于原因的 instructions（“做 X，因为 Y 往往导致 Z”）比僵硬指令（“始终做 X，绝不做 Y”）效果更好。当 model 理解目的时，会更可靠地遵循 instructions。
- **打包重复工作。** 如果每次测试运行都独立编写类似辅助 script（图表构建器、数据解析器），这就是应将 script 打包进 skill 的 `scripts/` directory 的信号。参阅[使用 script](/skill-creation/using-scripts)了解做法。

### 循环

1. 将 eval 信号和当前 `SKILL.md` 交给 LLM，并要求它提出改进。
2. 审查并应用修改。
3. 在新的 `iteration-<N+1>/` directory 中重新运行所有测试用例。
4. 评分并聚合新结果。
5. 进行人工审查。重复。

当你对结果满意、反馈持续为空，或迭代之间不再出现有意义改进时，就可以停止。

<Tip>
[`skill-creator`](https://github.com/anthropics/skills/tree/main/skills/skill-creator) Skill 自动化了这个 workflow 的大部分内容：运行 eval、为 assertion 评分、聚合 benchmark，并展示结果供人工审查。
</Tip>
