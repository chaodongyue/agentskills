只有 skill 被激活时，它才有帮助。`SKILL.md` frontmatter 中的 `description` field，是 agent 决定是否为某个 task 加载 skill 的主要机制。 description 不够具体意味着该触发时不会触发；description 过宽则意味着不该触发时也会触发。

本指南介绍如何系统地测试和改进 skill 的 description 的触发准确性。

## Skill 触发的工作原理

agent 使用[progressive disclosure](/specification#progressive-disclosure)来管理 context。启动时，它们只加载每个可用 skill 的 `name` 和 `description`，刚好足以判断某个 skill 何时可能相关。当 usertask 匹配某个 description 时，agent 会把完整的 `SKILL.md` 读入 context 并遵循其中 instructions。

这意味着触发责任完全落在 description 上。如果 description 没有传达 skill 什么时候有用，agent 就不会知道该使用它。

一个重要细节是：agent 通常只会在 task 需要超出自身基础能力的知识或能力时才查看 skills。像“阅读这个 PDF”这样的简单单步请求，即使 description 完全匹配，也可能不会触发 PDF skill，因为 agent 可以用基础 tool 处理。涉及专业知识的 task（陌生 API、领域特定 workflow 或不常见格式）才是优秀 description 能发挥作用的地方。

## 编写有效 description

在测试之前，先了解好 description 的样子会很有帮助。几个原则：

- **使用祈使句。** 把 description 写成给 agent 的指令：“Use this skill when...”，而不是“This skill does...”。 agent 正在决定是否行动，所以要告诉它何时行动。
- **关注 user 意图，而不是实现。** descriptionuser 想实现什么，而不是 skill 的内部机制。 agent 会拿 description 与 user 请求进行匹配。
- **宁可更主动一些。** 明确列出 skill 适用的 context，包括 user 没有直接说出领域名称的情况：“even if they don't explicitly mention 'CSV' or 'analysis.'”
- **保持简洁。** 几句话到一小段通常合适：足够覆盖 skill 范围，又不会在许多 skills 中膨胀 agent context。[specification](/specification#description-field)强制限制为 1024 个字符。

## 设计触发 eval 查询

要测试触发效果，你需要一组 eval 查询，即真实感较强的 userprompt，并标注它们是否应该触发你的 skill。

```json eval_queries.json
[
 { "query": "I've got a spreadsheet in ~/data/q4_results.xlsx with revenue in col C and expenses in col D — can you add a profit margin column and highlight anything under 10%?", "should_trigger": true },
 { "query": "whats the quickest way to convert this json file to yaml", "should_trigger": false }
]
```

目标是约 20 个查询：8 到 10 个应触发，8 到 10 个不应触发。

### 应触发查询

这些查询用于测试 description 是否覆盖了 skill 的范围。请沿多个维度变化：

- **表达方式**：有些正式，有些随意，有些带错别字或缩写。
- **显式程度**：有些直接点名 skill 领域（“analyze this CSV”），另一些只 description 需求但不点名（“my boss wants a chart from this data file”）。
- **细节量**：混合简短提示和 context 丰富的提示，例如简短的 “analyze my sales CSV and make a chart”，以及包含 file 路径、列名和背景故事的较长消息。
- **复杂度**：改变步骤数和决策点数量。把单步 task 和多步骤 workflow 都纳入进来，以测试当 skill 对应 task 埋在更长链路中时，agent 是否能判断其相关性。

最有用的应触发查询，是那些 skill 会有帮助、但仅从查询本身看关联并不明显的情况。这些正是 description 措辞能产生差异的地方。如果查询已经精确要求 skill 做的事情，那么任何合理 description 都会触发。

### 不应触发查询

最有价值的负面测试用例是**近似但不匹配**的查询：它们与你的 skill 共享关键词或概念，但实际需要的是另一件事。这些用例测试 description 是否精准，而不仅仅是宽泛。

对于 CSV 分析 skill，较弱的负面示例包括：

- `"Write a fibonacci function"`：明显无关，测试不到什么。
- `"What's the weather today?"`：没有关键词重叠，太容易。

强负面示例：

- `"I need to update the formulas in my Excel budget spreadsheet"`：共享“电子表格”和“数据”概念，但需要 Excel 编辑，而不是 CSV 分析。
- `"can you write a python script that reads a csv and uploads each row to our postgres database"`：涉及 CSV，但 task 是数据库 ETL，不是分析。

### 真实感建议

真实 userprompt 包含通用测试查询所缺少的 context。请包含：

- file 路径（`~/Downloads/report_final_v2.xlsx`）
- 个人 context（`"my manager asked me to..."`）
- 具体细节（列名、公司名、数据值）
- 随意语言、缩写和偶尔的错别字

## 测试 description 是否触发

基本方法是：安装 skill 后，让 agent 运行每个查询，并观察它是否调用该 skill。确保 skill 已注册并能被 agentdiscovery。具体方式因 client 而异（例如 skills directory、配置 file 或 CLI 标志）。

大多数 agent client 会提供某种可观测性能力，例如 execution 日志、 tool 调用历史或详细输出，让你看到运行期间咨询了哪些 skills。请查看你的 clientdocumentation 了解详情。如果 agent 加载了你的 `SKILL.md`，instructions skill 已触发；如果 agent 没有查看它就继续 execution，则 instructions 未触发。

查询在以下情况下“通过”：
- `should_trigger` 为 `true` 且 skill 被调用，或
- `should_trigger` 为 `false` 且 skill 未被调用。

### 多次运行

model 行为具有不确定性：同一个查询可能一次触发 skill，下一次却不触发。请多次运行每个查询（3 次是合理起点），并计算**触发率**：skill 被调用的运行占比。

应触发查询在触发率高于阈值时通过（0.5 是合理默认值）。不应触发查询在触发率低于该阈值时通过。

20 个查询每个运行 3 次，就是 60 次调用。你会希望把它 script 化。下面是总体结构：将 `check_triggered` 中的 `claude` 调用和检测逻辑替换为你的 agent client 提供的方式：

```bash
#!/bin/bash
QUERIES_FILE="${1:?Usage: $0 <queries.json>}"
SKILL_NAME="my-skill"
RUNS=3

# This example uses Claude Code's JSON output to check for Skill tool calls.
# Replace this function with detection logic for your agent client.
# Should return 0 (success) if the skill was invoked, 1 otherwise.
check_triggered() {
 local query="$1"
 claude -p "$query" --output-format json 2>/dev/null \
 | jq -e --arg skill "$SKILL_NAME" \
 'any(.messages[].content[]; .type == "tool_use" and .name == "Skill" and .input.skill == $skill)' \
 > /dev/null 2>&1
}

count=$(jq length "$QUERIES_FILE")
for i in $(seq 0 $((count - 1))); do
 query=$(jq -r ".[$i].query" "$QUERIES_FILE")
 should_trigger=$(jq -r ".[$i].should_trigger" "$QUERIES_FILE")
 triggers=0

 for run in $(seq 1 $RUNS); do
 check_triggered "$query" && triggers=$((triggers + 1))
 done

 jq -n \
 --arg query "$query" \
 --argjson should_trigger "$should_trigger" \
 --argjson triggers "$triggers" \
 --argjson runs "$RUNS" \
 '{query: $query, should_trigger: $should_trigger, triggers: $triggers, runs: $runs, trigger_rate: ($triggers / $runs)}'
done | jq -s '.'
```

<Tip>
如果你的 agent client 支持，可以在结果明确后提前停止运行：agent 要么已经咨询了 skill，要么已经开始在没有 skill 的情况下工作。这可以显著降低运行完整 eval 集的时间和成本。
</Tip>

## 通过训练/validation 拆分避免过拟合

如果你针对所有查询 Optimizing descriptions，就有过拟合风险：写出的 description 适用于这些特定措辞，却无法泛化到新措辞。

解决方法是拆分查询集：

- **训练集（约 60%）**：用于识别失败并指导改进的查询。
- **validation set（约 40%）**：单独留出，只用于检查改进是否能泛化的查询。

确保两个集合都按比例包含应触发和不应触发查询，不要意外把所有正例放进同一个集合。随机打乱，并在各次迭代中保持拆分固定，这样比较才公平。

如果你使用类似[上面](#running-multiple-times)的 script，可以把查询拆成两个 file：`train_queries.json` 和 `validation_queries.json`，然后分别对它们运行 script。

## 优化循环

1. **eval**当前 description 在*训练集和 validation set*上的表现。训练结果指导你的修改；validation 结果告诉你这些修改是否泛化。
2. **识别训练集中的失败**：哪些应触发查询没有触发？哪些不应触发查询触发了？
 - 只使用训练集失败来指导修改。无论你是自己修订 description 还是提示 LLM，都不要把validation set结果纳入修改过程。
3. **修订 description。** 重点放在泛化：
 - 如果应触发查询失败，description 可能过窄。扩大范围，或添加 skill 何时有用的 context。
 - 如果不应触发查询误触发，description 可能过宽。更具体地 instructions skill *不*做什么，或明确它与相邻能力之间的边界。
 - 避免添加失败查询中的具体关键词，那是过拟合。应找出这些查询所代表的一般类别或概念，并处理该类别。
 - 如果几轮迭代后仍卡住，请尝试结构上不同的 description 方式，而不是继续微调。不同的框架或句子结构可能带来突破。
 - 检查 description 是否仍低于 1024 字符限制，因为 description 在优化过程中往往会变长。
4. **重复**步骤 1 到 3，直到所有*训练集*查询通过，或不再看到有意义的改进。
5. **按 validation 通过率选择最佳迭代**，也就是*validation set*中通过查询的比例。注意，最佳 description 不一定是最后产生的 description；较早迭代可能比后来对训练集过拟合的版本有更高 validation 通过率。

五轮迭代通常足够。如果表现没有改善，问题可能在查询本身（太容易、太难或标注不佳），而不是 description。

<Tip>
[`skill-creator`](https://github.com/anthropics/skills/tree/main/skills/skill-creator) Skill 会端到端自动化这个循环：拆分 eval 集、并行 eval 触发率、使用 Claude 提出 description 改进，并生成可在运行时查看的实时 HTML 报告。
</Tip>

## 应用结果

选出最佳 description 后：

1. 更新 `SKILL.md` frontmatter 中的 `description` field。
2. 确认 description 低于 [1024 字符限制](/specification#description-field)。
3. 确认 description 按预期触发。手动尝试几个 prompt，做快速健全性检查。若要更严格测试，请编写 5 到 10 个新查询（混合应触发和不应触发），并通过 evalscript 运行。由于这些查询从未参与优化过程，它们能诚实检验 description 是否泛化。

前后对比：

```yaml
# Before
description: Process CSV files.

# After
description: >
 Analyze CSV and tabular data files — compute summary statistics,
 add derived columns, generate charts, and clean messy data. Use this
 skill when the user has a CSV, TSV, or Excel file and wants to
 explore, transform, or visualize the data, even if they don't
 explicitly mention "CSV" or "analysis."
```

改进后的 description 更具体地 instructions 了 skill 做什么（汇总统计、派生列、图表、清洗），也更宽泛地 instructions 了何时适用（CSV、 TSV、 Excel；即使没有显式关键词）。
